# Preliminary intake — migrating the engine to Rust

> **Not an order. The Regent's motivation, verbatim:** *"controle da alma do
> negócio é o principal. façamos isso para não nos enrolarmos depois: não é
> questão do javascript não conseguir fazer as coisas, é principalmente porque
> o Rust faz além, e a tipagem rigorosa me importa."* Two claims, and neither
> is about capacity: **(1)** stricter control over the engine's core logic, in
> the sense of *verifiable correctness*; **(2)** strong static typing as a
> value in itself, not as the fix for a measured defect. This document applies
> to those two claims the method applied to every proposal today — the
> strongest case for, the strongest case against, both priced — and it does
> not refuse and does not ratify. Engine 3.4.7.05 at `49c392a`; measurements
> 2026-09-11, Node 22.17.1, `bench.mjs` in the session scratchpad.

## 1. What the argument is not — capacity, measured and set aside

So that it is never re-argued: JS is not near any capacity limit this project
has or has described.

| input | size | parse | parse + XML | burn `.hgml` | all four projections + inverse |
|---|---|---|---|---|---|
| `ORD-0010` | 4.8 KB | 0.67 ms | 0.94 ms | 1.43 ms | **4.3 ms** |
| `ORD-2026-08-30-01` | 12.3 KB | 0.25 ms | 0.80 ms | 0.93 ms | **3.4 ms** |
| 100 × the larger, concatenated | 1.2 MB | — | 95 ms | 102 ms | — |

Linear (`O(c·n)`, `INTAKE-FORMAL-ANALYSIS.md` §1.1), 12 MB/s; 100 MB would take
~8 s. Cold CLI 146 ms, of which the engine is < 1 ms and Node the rest. Heap
31 MB. The workload is 5–12 KB Orders a few times a day and a browser editor
at 1 ms per keystroke. Performance is not on either side of the scale below.

## 2. What a compiler would verify *here* — the argument, made concrete

Claim (1) is only as strong as the list of things the engine promises that a
compiler could check. The list, measured against the code, with what each of
three regimes gives — **Rust**, **typed JS** (JSDoc + `tsc --checkJs`: a dev
tool, no runtime change, no build, the browser loads the same files), and
**today** (JS + the corpus):

| promise the engine makes | where it lives today | Rust | typed JS | today |
|---|---|---|---|---|
| a node is exactly one of five kinds: command, literal, text, `[raw]`, `[logic]` | **62 duck-typed checks** — `nd.canonical`×31, `.logic`×12, `.text`×7, `.literal`×7, `.rawFence`×5; no tag, kind = which property exists | `enum Node`, exhaustive `match` in each of 5 projections | discriminated union + `never` check — equivalent, if the tag is added | corpus catches the forgotten case only if an input exercises it |
| every projection handles all four edge kinds `nest \| conj \| seq \| chain` (`I_C4`, `HGML_CONVERGENCE` §6) | string compares, per emitter | exhaustive | exhaustive | corpus |
| absence is `<needs>`, never a crash | **43 hand-written null guards** (`opts && opts.x`, `== null`) | `Option<T>` — the compiler refuses the unguarded read | `strictNullChecks` — equivalent | the guard that is missing is found in production |
| **projections read the AST, never write it** — *the* central rule (`CLAUDE.md`: the AST is the source of truth) | discipline; three writes past the emitters (`burn.js` on a fresh formula parse, `inverse` on its own copy) — honoured, unenforced | `fn to_xml(ast: &Ast)` — a write is a compile error; ownership is the rule made mechanical | `Readonly<>` is shallow and cast-around; not enforceable | corpus cannot see it; a mutation that leaves bytes identical is invisible |
| stores have a shape (`expansions.json`, `rules.json`, `templates.json`) | generated by `build-templates.js`; loaded untyped; a hand-edited store fails at first use | `serde` — refused at load, with the field named | types describe the shape; nothing checks it at load (types are erased) | `dag.js` for one of the three |
| commands have a valency (`SIGNATURES.md`) | `FRAMES` **models the first slot only**; *"arity-2 signatures … FRAMES only models the first slot"* (parser comment) | a signature type forces every slot to be represented | same — the type forces the second slot into existence | the second slot is a comment |
| `ck` is a 64-bit checksum | **two 32-bit FNV-1a runs**, because JS has no 64-bit integer; a design decision the language forced | `u64`, one FNV-1a | unchanged: still no `u64` | — |
| names are not strings: `CommandName`, `OrderId`, `EdgeKind` | strings everywhere | newtypes; a command name cannot be passed where an Order id is due | branded types — weaker, opt-in | — |
| `β` terminates; `D` is acyclic; `φ_w = φ_r` (`I_C1`, `I_C3`) | proof on paper; `dag.js`; gate to add | **not a type property in any language** — runtime data, runtime gate | same | same |
| the burn is a normal form (`I_C5`), AHU canon | algorithm + property test | `proptest` generates the inputs | hand-written, as today | hand-written |

Read the table honestly and it splits in three:

- **Typed JS gives** the first three rows and the valency row — the bulk of
  claim (1)'s *exhaustiveness and nullability* — at a cost of annotations, no
  rewrite, no toolchain in the runtime, no change to what the browser loads.
- **Only Rust gives** the AST-immutability row, typed deserialisation, `u64`,
  and newtypes the compiler will not let you cast around. The first of those
  is the project's central rule; today it is honoured by discipline, and the
  discipline has held (three writes, all on copies).
- **Neither gives** the theorems. `β`'s termination, acyclicity and the
  dialect property are facts about *data*; the gates for them are runtime
  checks in any language, and they are the ones that actually failed today.

## 3. The steelman — the strongest case for Rust, on the corrected motivation

**S1 — "controle da alma do negócio" has one exact meaning here, and Rust is
the only regime that enforces it.** The engine's soul is the AST plus the rule
that projections *read* it. `&Ast` versus `&mut Ast` is that rule as a type;
no annotation regime in JS can say it and mean it. Everything else the
project calls a projection — XML, `GlyphAST`, `.hgml`, the inverse, the
future mini-repo, `relates[]` — is a reader, and the compiler would know.

**S2 — the engine now lives on invariants, and the ones a compiler owns are
the cheap half.** Fifteen invariants were stated today. The exhaustiveness
and nullability ones are the ones that *silently* fail — a missing `match`
arm produces wrong bytes, not an exception — and they are exactly the ones a
type system makes impossible rather than improbable. The corpus finds them
only where an input happens to reach them.

**S3 — typing as a value is a legitimate reason and the study cannot price
it down.** The Regent's second claim is not a hypothesis; it is a preference
about what kind of code the soul of the business is written in. A study can
say what it costs. It cannot say it is wrong.

**S4 — "para não nos enrolarmos depois."** Every line written in JS from
here is a line ported later. The seam graph shows the engine is 3 569 lines
today and the design just added three fronts (A, B, C) to it. The cheapest
port is the earliest one, *after* the map exists (§6).

**S5 — the second host stops being a constraint on the core.** WASM gives
one core to CLI, browser, and any future host; `glyph-ui.js` becomes a thin
consumer of a typed boundary instead of the co-owner of a global.

**S6 — `u64`, `serde`, `proptest`.** Three places where the language shaped
a design decision or the test regime — the checksum, the store loading, the
invariance tests — and where Rust's answer is the direct one.

## 4. The defeater — the strongest case against

**D1 — the cost is ~9 000 lines, a toolchain, and the distribution model.**
Rewrite: parser 3 569, `test-corpus.js` 2 487 (the acceptance of everything),
`build-templates`, `build-skill`, `dag`, `check-globals`, `glyph-diff`,
`glyph-trace` — ~7 800 lines that *are* the engine and its gates.
`glyph-ui.js` (1 775) stays JS and gains a WASM boundary crossed by
`serializeAST`, `walk`, `tokenize`, `suggest`. Then `cargo`, `wasm-bindgen`,
a `target/`, a build before any check, and per-platform binaries or a
compile for every agent that today runs `node scripts/glyph-cli.js` from
the skill's own copy of the source. **"Zero dependências — é propriedade do
repositório, não acidente. Não haverá"** — not a `dependency` in
`package.json`, but a compiler and a build artefact the browser must be
served. The skill ships the engine as readable source today; it would ship a
`.wasm` or a build instruction.

**D2 — typed JS delivers most of claim (1) for three orders of magnitude
less.** §2's table: exhaustiveness, nullability, the valency slot, typed
`opts`, typed store *shapes* — annotations on the code that exists, checked
by a dev tool, zero runtime change. What it does not deliver is four rows —
AST immutability, load-time deserialisation, `u64`, uncastable newtypes —
and the question the Regent is actually deciding is whether **those four**
are worth D1. That is a fair question; it is a much smaller one than
"Rust or JS".

**D3 — the failures the study found are not type failures.** Nine formulas
in the wrong dialect (data against prose), a 3 569-line file, a stale
`.plan` line, two ID schemes, a false "cached" claim. A Rust engine would
carry all of them. The gates that catch them — comma depth, seam graph, link
graph, ID uniqueness — are runtime checks over data in either language. The
compiler's territory (§2, first block) has produced **zero** recorded
defects; the corpus's territory has produced today's whole list.

**D4 — a port now ports the wrong semantics, twice.** Nine formulas are
undecided; V6 is untested; the Orders' identity is unsettled; `relates[]` is
designed, not built. A port made before those settle either freezes them into
a second implementation or lands each decision twice. The project's own rule
— *AST is the source of truth; projections follow* — says: settle the truth,
then re-project. The **corpus is the oracle** of any port (byte-identical
XML/AST/`.hgml`), and an oracle whose expected bytes are about to change
cannot certify a port.

**D5 — the discipline S1 would enforce has not failed.** Three writes past
the emitters, all on fresh copies. The rule is honoured by convention, and the
convention has a perfect record. Enforcing a rule nobody broke is worth
something; it is not worth the same as fixing a rule someone did.

**D6 — S5's premise expired this week.** `"type": "module"` is already in
`package.json` *so the core can be split into files the browser loads without
a bundler*. The split (`INTAKE-PARSER-SPLIT.md`) ends the one-file constraint
in JS. WASM ends it again, at D1's price.

## 5. What would be measured — since the value itself cannot be

Claim (2) is a value; no threshold applies to it, and this study does not
pretend one does. Claim (1) can be *narrowed* to the four Rust-only rows, and
those can be priced against the alternative:

| question | how it is answered | cost to answer |
|---|---|---|
| how much of §2 does typed JS actually deliver on this code? | annotate `burn.js` (250 lines) and `emit-xml.js` after the split; count what `tsc --checkJs` refuses on first run | one afternoon; zero runtime change |
| has a projection ever written the AST? | a `--check` that deep-freezes the parsed segments before each emitter in `test-corpus.js`; run the corpus | ~20 lines; answers D5 with a number |
| does the second valency slot matter? | count commands in `SIGNATURES.md` with arity 2 whose second slot is unchecked today | one grep |
| what does the skill's consumer need — source or binary? | which agents run `node scripts/glyph-cli.js` from the skill copy, and whether they have `cargo` | the Regent knows; the study does not |

If the first answer is "typed JS refuses nothing the corpus had not already
caught" and the second is "never", claim (1) reduces to `u64` and newtypes.
If the first refuses real defects, claim (1) is confirmed *and* mostly served
without a port. Either way the port's case gets sharper, not weaker.

## 6. Ordering, whatever is decided — and the plan if it is Rust

The split comes first under every outcome: a port needs the dependency map
and module boundaries, and the seam graph plus twelve files *are* that map.
Then the table settles (nine formulas), so the corpus's expected bytes are the
right ones. Those two steps are this week's work with or without Rust.

**If the Regent decides Rust**, the plan the study can stand behind:

1. **The JS engine becomes the reference implementation.** It is the oracle:
   the Rust port passes when `test-corpus.js`'s inputs produce byte-identical
   XML, `GlyphAST` and `.hgml` from both. The corpus stays JS; it tests both.
2. **Port in the seam graph's order, leaves first, one module per step** —
   `util`, `emit-ast`, `inverse`, `burn`, … — JS and Rust coexisting at the
   module boundary the split created. Each step has its own oracle (the JS
   module it replaces) and its own green.
3. **The browser keeps the JS core until WASM is proven** on the same corpus
   from inside the page. Zero-dependency ends only when the WASM build is the
   one the app serves — and that is a separate decision from the CLI's.
4. **Typed JS first anyway** — the annotations written for §5's measurement
   are the port's specification, module by module.

**Recommendation, which is not a ratification.** The corrected motivation is
a stronger argument than "não dá conta", and §2 says exactly where it is
strongest: the AST as `&Ast`. That one row is real, is the project's central
rule, and no JS regime enforces it. Against it stands D1, whole. The study's
position: run §5 first (an afternoon), split first (this week), settle the
table (the Regent's nine lines), and take the Rust decision with §5's numbers
and the module map in hand — where it costs the same to say yes and less to
be right. The value in claim (2) does not expire while that happens; the
cost in D1 does not shrink, but the port that would pay it gets a map and an
oracle it does not have today.
