# Intake — the exit of the JS

> **The measured proposal for step 12 of the trail to the final Explorer**
> ([`.plan`](../.plan/README.md) §5): the target is the Glyph 100% in Rust — the
> engine, the core of the app and the skill — with the JS leaving piece by piece, each
> piece when the Rust passes the oracle on it. The page's own route is measured in
> [`INTAKE-EXPLORER.md`](INTAKE-EXPLORER.md) §4. This file takes the inventory of what
> is still JS and asks what leaves, in what order, and what holds the Rust once the JS
> that wrote the oracle is gone. It opens no Order. Measured at `5685486`.

## 1. What is still JS

Every `.js` under `scripts/`, by role, in lines, with the module of the
[`ladder.toml`](../.plan/ladder.toml) that ports it:

| role | files | lines | the Rust |
|---|---|---|---|
| the engine | `glyph-parser.js`, the 13 modules of `scripts/core/` | 4,625 | ported, crate by crate, each held to the oracle; M07a to M10d `started` |
| its data | `glyph-data.js`, generated by `build-templates.js` | 1,505 | the stores the Rust reads directly |
| three tools | `glyph-check.js` 327, `glyph-diff.js` 186, `glyph-trace.js` 129 | 642 | **not ported**: `glyph-schema`, `glyph-diff` and `glyph-trace` are crates with a doc comment and no code; M10e, M10f and M10g are `open`, and each `closes_when` already says what *the same* means |
| the command line, the protocol, the zip | `glyph-cli.js` 231, `glyph-protocol.js` 134, `glyph-zip.js` 124 | 489 | ported: the binary answers the CLI's flags (M11), the protocol, and the bundle (M10h) |
| the slash commands | `glyph-plugin.js` | 110 | none |
| the page's interface | `glyph-ui.js`, `glyph-moulds.js`, `glyph-transport.js` | 2,138 | the route of [`INTAKE-EXPLORER.md`](INTAKE-EXPLORER.md) §4; the ladder holds M11b, *the core in the browser*, `open` |
| the repository's tooling | the builders, the checks, the graphs, the measurements, `serve-dev.js`, and `test-corpus.js` (4,608 alone) | 6,733 | none, and the target does not name it |

**The skill** runs the JS: its commands are `node scripts/glyph-parser.js …`, and the
plugin `npm run plugin` packs carries the JS engine. It runs wherever node runs, the cloud
sessions included. **The binary** links no crate and builds with plain `cargo build` on
each system; its `--install` is Windows-only (`%LOCALAPPDATA%`, `reg.exe`). Nothing in
the repository builds it for another system: there is no CI.

**The oracle** is exported from the JS at every `npm run check:rust`
(`test-corpus.js --export-oracle`, 119 sources), and the Rust is tested against it. The
JS engine is the oracle's writer, so it is the last thing that can leave.

## 2. The questions

**J1. What leaves.**
- a. the engine, the three tools, the slash commands and the skill; the repository's
  tooling stays JS, so node stays for whoever builds the repository and never for
  whoever uses Glyph
- b. everything, the tooling included: 6,733 lines, `test-corpus.js` among them
- c. a, and each tooling script leaves when an Order touches it

**J2. What holds the Rust once the JS engine is gone.**
- a. **the oracle frozen**: the last export is committed beside the Rust tests, and a
  change to the expected bytes is an edit of those files, made by the Order that moves
  them
- b. **conformance vectors written from the spec** (T2): `conformance/golden.json` grows
  until it covers what the oracle covered
- c. **both**: frozen when the JS leaves, and vectors written from the spec as each
  Order touches a source

**J3. The order of the exit.**
- a. the three tools first (M10e, M10f, M10g: 642 lines, the criterion of each already
  written); then the skill and the slash commands; then the page; the engine last, when
  nothing loads it
- b. the page first, since it carries the engine to the user; then the tools, the
  skill, and the engine

**J4. How the skill reaches the binary.**
- a. the plugin carries one `glyph` per system, built for each by a pipeline the
  repository does not have yet
- b. the skill calls an installed `glyph`, and refuses by name where none is installed;
  the install grows to Linux and macOS in the same Order
- c. the skill stays on the JS until the engine leaves (J3)

**The session's recommendation:** J1 a, J2 c, J3 a, J4 b.
- **J1 a** takes node away from the user, which is what the target is for, and leaves the builders alone, since nothing measured asks for them to move.
- **J2 c** keeps a byte-for-byte guard from the first day, and grows the guard the spec owns (T2).
- **J3 a** starts where the criterion is written and the cost is smallest.
- **J4 b** needs no pipeline. The binary already links no crate and installs itself, and Windows is where the Regent runs it.
