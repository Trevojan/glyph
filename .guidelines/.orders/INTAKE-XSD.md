# Intake — the XSD the engine generates, and the gate that holds it to the XML

> **The measured proposal for step 1 of the trail to the final Explorer**
> ([`.plan`](../.plan/README.md) §5). The norm is signed: the XSD is generated by the
> engine, never written by hand, and a gate checks it against the XML's content, with
> divergence at `fix` ([`INTAKE-EFFECTS.md`](INTAKE-EFFECTS.md) §8.1, the Regent on
> 2026-11-07). This file measures what the engine emits and asks what the norm leaves to
> decide. The Regent answered §4 on 2026-11-21, and §5 holds the answers: the step is
> two Orders, one per engine's validator, and the first opens once the open slot is free.
> Measured at `5685486`.

## 1. What the engine emits today

Measured over the 119 declared sources of the snapshot, through the oracle that
`npm run check:rust` exports (`rust/target/oracle/`), every XML parsed by a standard
parser:

| | |
|---|---|
| distinct elements | 96, every source parses |
| parent → child pairs | 235 |
| attributes, per element | 36 |
| `<schema>` | empty in all 119: `scripts/core/emit-xml.js:36` writes it as a constant |
| sources with something to declare | 30: a template in 26, `binds` on `<iterate>` in 5 and on `<validate>` in 6, a `<variable>` in 1, a named `<section>`, `<block>` and `<part>` in 1 each |
| elements [`XML_REFERENCE.md`](../.sources/XML_REFERENCE.md) names | 139 (each written as `` `<name `` there); 92 of them emitted by the corpus, 47 never, the retired `skeptic` among them; 4 emitted elements (`invoke`, `reads`, `source`, `uses`) are not written that way there |
| what `--bundle` writes | five files: `.pgml`, `.xml`, `.json`, `.hgml` and the `.manifest.json` |

**No XSD exists in the repository, and no XML validator runs anywhere.** The JS side has
zero dependencies by decision, and the Rust side grades every crate by the rule of
2026-09-27 (O7), which `crate-weight.js` holds in `check:rust`.

**The precedent is the AST's.** [`ast-schema.json`](../.sources/ast-schema.json) gives
the shape of a `GlyphAST` envelope, and it is hand-authored on purpose: *"a schema
derived from the engine cannot catch the engine."* `scripts/glyph-check.js` validates an
envelope against it in 327 lines; its Rust port, `glyph-schema`, is a crate with a doc
comment and no code.

## 2. Three schemas, and the one the norm names

| schema | what it describes | who writes it | where it stands |
|---|---|---|---|
| **the ORD's** | what one Order declares: its sections, blocks, parts, templates and variables | the engine, from the Order's tree | the norm's XSD — *"the handmade part is the ORD; the XSD is the engine's answer about it"* — and the `<schema>` decision of 2026-10-15 name this one; neither is built |
| **the series'** | the pattern every Order of an EMS follows | the user, as configuration | the first field of the `EMS.json`, step 2 of the trail ([`INTAKE-PIN-TRAFFIC.md`](INTAKE-PIN-TRAFFIC.md) §5) |
| **the language's** | which elements and attributes any `<glyph-package>` may hold | by hand, like `ast-schema.json` | in prose today, in `XML_REFERENCE.md`, held to the engine by D-03; the norm does not name it |

**Why the gate is not redundant.** When the engine writes the XML and the ORD's schema
from one tree, the two agree by construction. They diverge when the XML comes from
outside the engine: an XML edited by hand and read back by `fromXML`, a bundle an older
engine wrote, or an Order the Explorer edits. The gate is the check at that trust
boundary, which is never skipped as unnecessary.

## 3. What any answer costs

| if the schema travels | moves |
|---|---|
| inside the package, in `<schema>` | the `xml` hash of the 30 sources that declare something (§1); the other 89 keep `<schema/>` |
| beside it, as `ORD-####.xsd` in the bundle | no hash of the snapshot; the bundle grows by one file, and the manifest lists it |
| only on request, from a flag | nothing stored, and nothing for the gate to read later |

A generator and a validator for the subset the engine emits are each about the size of
`glyph-check.js` in each engine, by that comparison; nothing is built to measure them
against.

## 4. The questions

**X1. What the generated XSD describes.**
- a. **the ORD's declaration**: its sections, blocks, parts, templates and variables, as
  the norm and the `<schema>` decision of 2026-10-15 say. The language's schema stays in
  `XML_REFERENCE.md`
- b. **the language**: every element and attribute a package may hold, generated from
  the vocabulary. The AST's precedent says a schema derived from the engine cannot catch
  the engine
- c. **both**: the language's schema by hand, as the base, and the ORD's declaration
  generated as a restriction over it

**X2. Its notation.**
- a. **W3C XSD**, only the subset the engine needs: `xs:element`, `xs:complexType`,
  `xs:sequence` and `xs:choice`, `xs:attribute`, `minOccurs` and `maxOccurs`. Any XML
  tool reads it
- b. **Glyph's own declaration inside `<schema>`**, the form of 2026-10-15, with *XSD*
  naming that declaration
- c. **both**: `<schema>` declares, and the XSD is generated from it as a projection

**X3. Where it travels.** The three rows of §3.
- a. inside the package, in `<schema>`
- b. beside it in the bundle, as `ORD-####.xsd`
- c. only on request, from a flag

**X4. What validates the XML against it**, at `fix` as signed.
- a. **the engine's own validator**, for the subset the engine generates, in both
  engines and held by the oracle: no dependency
- b. **an external validator** such as `xmllint`, run by `npm run check` when it is
  installed: the zero-dependency rule holds for the engine, not for the check
- c. **a Rust crate**, graded by O7 in `crate-weight.js` before it enters

**X5. Where the gate runs.**
- a. where an XML enters from outside the engine: `fromXML`, and a bundle read back
- b. a, and also over every bundle under `.orders/` in `npm run check`
- c. only on request

**X6. Which engine builds it.**
- a. both, the JS first, as the reference, as every Order since `EMS-002/ORD-0001`
- b. the Rust only, held by conformance vectors written from the spec (T2), since the
  JS is leaving piece by piece

**The session's recommendation:** X1 a, X2 c, X3 a, X4 a, X5 b, X6 a.
- **X1 a** is the norm's own reading.
- **X2 c** keeps one source, the declaration, and makes the Regent's *XSD* its projection. That projection is written only when a tool asks for it, since no format enters without a consumer that parses it.
- **X3 a** lets the gate read the schema from the document it checks; under it, 30 hashes move and 89 stay.
- **X4 a** keeps the zero-dependency rule whole.
- **X5 b** catches a bundle that drifts while it sits in the repository.
- **X6 a** follows the oracle until the JS leaves.
